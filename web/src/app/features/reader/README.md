# Reader Image Loading Flow (ReaderComponent + ReaderService)

---

## 1] DEFINITIONS

**P = {p₁, p₂, ..., pₙ}**

* массив всех страниц

- по факту: это просто огромный список картинок, но без самих картинок, только инфа... якобы мета дата (pagesMeta)

**pᵢ.src = ∅**

* картинок нет, только "заглушки", типа "я есть, но меня нет"

**I: id => индекс**

* чтобы не искать как идиот по массиву, создается мапа - сразу знаем где страница

**V ⊆ P - visiblePages**

* то, что реально сейчас в DOM, остальное нахрен не рендерим (для оптимизации, вечно перезаполняем используя актуальный массив P)

---

## 2] INITIALIZATION (OPEN / ПРИ ОТКРЫТИИ)

**P <= pagesMeta**

* загрузили только метаданные - быстро, без картинок, для снятия нагрузки на память

**I(p.id) = index => O(1) = берем, без перебирания**

* сразу стоится карта, чтобы потом не бегать O(n) как еблан

**c = currentPage**

* точка старта - куда скроллить

**V = окно вокруг c**

* не грузим всё, только кусок, иначе браузер скажет "adios... puta madres"

### RESET:

* СВЯЩЕННАЯ ЧИСТКА:

- загрузки
- кеш
- токены
- visibleUnloadedCount (счётчик того, что юзер реально видит незагруженным)

* для облегчения аля "двай по новой, все херня"

+ есть режимы обновления:
- open = полный ресет
- merge = мягкое обновление без сброса скролла
- reset = очистка состояния

---

## 3] WINDOW (отрисованный запас вокруг)

**V = кусок массива вокруг центра**

* не грузить 10000 картинок, достаточно ~120
* всё остальное катится в тартарары

---

## 4] INTERSECTION OBSERVER

(что сейчас или скоро попадёт в экран - датчик движения перед глазами хз)

**Брать только элементы, которые попали в зону видимости (или рядом с ней)**

* браузер говорит, что видно, а я решаю, что грузить

### rootMargin:

```
iOS:     1500px
остальные: 2500px
```

* было 600/1200 - мало, картинки не успевали
* теперь грузится сильно заранее, до того как пользователь вообще туда доскроллит
* threshold: 0 - срабатывает как только первый пиксель входит в зону, без лишних задержек

### Сортировка по центру

* чтобы грузить то, что ближе к глазам, а не где-то в жопе

+ центр может смещаться на focusPageId (при навигации)

---

### Ограничение:

Берется максимум:

**количество кандидатов = 2 × MAX_LOAD, где**
**MAX_LOAD = 12 - реальное количество параллельных задач**

* MAX_LOAD (12) ограничивает, сколько изображений грузится одновременно
* 2 × MAX_LOAD (24) ограничивает, сколько элементов рассматривается как кандидатов на загрузку
* иначе опять ебучая перегрузка или простой

---

## 5] LOADING (ленивая загрузка изображений)

### УСЛОВИЕ:

если не грузится и есть слот

* если уже грузится - не трогаем
* если лимит - не трогаем
* иначе - ехала!

---

### ШАГИ:

1. Добавить в loadingSet

   * пометили: "занят, не трогать"

2. Если нет src => грузить

   * лениво - только когда реально надо

3. Blob => сделать URL
   *(на айфоне ебучий стринг... я не ебу, он не умеет работать с блобами)*

   * браузер не умеет напрямую, поэтому костыль через URL

4. img.src = url

   * ебучая магия начинается...

5. ожидание load / error / timeout

   * потому что клятый браузер частенько так тупит как скот

6. cleanup

   * убрать из загрузки

7. проверка token

   * если устарел - выходим (защита от гонок)

---

## 6] MEMORY CLEANUP  (очистка памяти от лишних изображений)

**Взять текущую страницу k**

оставить диапазон:

```
iOS:       [k - 20, k + 20]
остальные: [k - 50, k + 50]
```

* было 30 везде - на iOS жрало память без толку, на десктопе наоборот чистило слишком агрессивно
* всё за пределами диапазона стирается

Удалить URL

* иначе память улетит в космос, особенно на ебучем айфоне

+ также чистка происходит при смене окна (visiblePages)

## 7] WINDOW SHIFT (сдвиг окна рендеринга)

Если пользователь близко к краю окна:

### ТО:

пересчитываем окно

* двигаем "камеру"

### И:

сохраняем скролл

* иначе будет дергание туда-сюда картинок

+ используется preserveScroll (якорь + компенсация scrollTop)

---

## 7.1] PRESERVE SCROLL (без дёргания при вставке страниц сверху)

### ПРОБЛЕМА:

при добавлении страниц в начало массива (prev-merge или сдвиг окна вверх)
DOM сдвигается вниз - а скролл остается на старом месте
итог: видимая область прыгает

### СТАРОЕ РЕШЕНИЕ (requestAnimationFrame):

```
до мутации:  запомнить rect.top якоря
после мутации: scrollBy(разница) в следующем кадре
```

* проблема: браузер успевает отрисовать кадр с прыжком до компенсации
* результат: мигание на 1 кадр, на телефоне особенно заметно

### НОВОЕ РЕШЕНИЕ (queueMicrotask):

```
до мутации:
  prevDelta = container.scrollTop - anchorEl.offsetTop

после мутации (queueMicrotask):
  container.scrollTop = newEl.offsetTop + prevDelta
```

* queueMicrotask выполняется до следующего paint - браузер не успевает отрисовать промежуточное состояние
* прыжок исчезает полностью

## 8] PARALLELISM

**C ≤ MAX_LOAD**

* тупо семафор ("максимум MAX_LOAD одновременно")
* больше нельзя, иначе браузер ёбнется

---

## 9] CHAPTER LOADING

Если близко к концу => подгружаем следующую
Если близко к началу => грузим предыдущую

* используется текущая глава (reader.chapterId), а не последняя загруженная

* есть защита:
- loadedChapterIds (чтобы не грузить повторно)
- fetchingNext / fetchingPrev (чтобы не было двойных запросов)

---

### ШАГИ:

1. Получить следующую главу

2. Получить её страницы

3. Убрать дубликаты

   * иначе будет каша

4. Склеить (Merge):

```
NEXT:
P = P + newPages

PREV:
P = newPages + P
```

* просто приклеили

---

## 10] CHAPTER TRACKING

Для каждой главы хранится диапазон страниц

* например: глава 5 = страницы 100–150

Когда пользователь на странице:

* проверка где он
* обновить chapterId

- обновляется только при видимости (observer)

---

**ВАЖНО:**
merge НЕ трогает chapterId

* потому что это логика "где читатель", а не "что загружено"

---

## 11] NAVIGATION

Когда переход:

1. найти индекс
2. обновить окно
3. перезагрузить соседей

   * чтобы не было "белых экранов"
4. скроллить
5. обновить state (reader.service)

+ observer временно блокируется (isNavigating)

+ делается preload вокруг целевой страницы

+ один requestAnimationFrame с принудительным reflow для точных offsetTop:

```js
void document.body.offsetHeight  // форсим layout перед измерением
```

* было два rAF подряд - лишний кадр задержки, смысла нет
* теперь один, но с гарантией что layout актуальный

+ ожидание появления DOM (waitForTarget)

## 12] TOKEN SYSTEM (защита от устаревших асинхронных операций)

Каждая загрузка имеет token

* типа версия

Если token устарел:

* "иди нахер, ты не актуален"

* это спасает от гонок! иначе ебнешься...

## 13] SCROLL PRELOAD (fallback для observer, потому что браузеры - это цирк)

### ПРОБЛЕМА:

IntersectionObserver - вроде умный, но:
* при скролле вверх может не срабатывать
* особенно Safari (ну тут без комментариев, ебаный зоопарк)

* результат:
картинки сверху не подгружаются = розовая хуйня вместо страницы

---

### РЕШЕНИЕ:

Добавлен **ручной scroll listener**
* костыль? да
* работает? да
* значит идем дальше

---

### КАК ЭТО РАБОТАЕТ:

При каждом scroll (но с throttle, чтобы не убить всё нахрен):

1. пройтись по всем `imgRefs`
2. взять `getBoundingClientRect()`
3. проверить, близко ли к viewport

```
iOS:       [-1500px, +1500px]
остальные: [-2500px, +2500px]
```

* совпадает с rootMargin observer-а - один и тот же порог везде, без рассинхрона

---

### ЕСЛИ:

* картинка не загружена
* не в loadingSet
* есть слот (MAX_LOAD)

* тогда:

**грузим вручную тем же pipeline, что и observer**

---

### ВАЖНО:

Этот механизм:

* НЕ заменяет observer
* НЕ конкурирует с ним
* а просто **страхует его, когда он тупит как скот**

---

### ОГРАНИЧЕНИЯ:

* соблюдает MAX_LOAD
* использует loadingSet
* уважает token систему
* работает через тот же ensure → url → img.src pipeline

---

### THROTTLING:

Чтобы не было:
> "ой, 500 scroll событий - давай всё грузить сразу... раздражает"

используется:

* `requestAnimationFrame`
* флаг `scrollPreloadThrottled`

* максимум 1 проход за кадр

---

## 14] LOADER (когда показывать спиннер, а когда нет)

### ИДЕЯ:

загрузки бывают двух типов:

```
фоновая (вне viewport):
  картинка далеко, юзер её не видит
  => грузить тихо, спиннер не трогать!

видимая (внутри viewport):
  картинка прямо перед носом, а там пусто
  => юзер реально ждёт => показывается спиннер
```

---

### КАК ОПРЕДЕЛЯТЬ "видимая" или нет:

```
isImageInViewport(img):
  rect.bottom > 0 && rect.top < window.innerHeight
```

* просто: входит в реальный экран - значит видимая
* rootMargin тут не при делах, только чистый viewport

---

### СЧЁТЧИК:

**visibleUnloadedCount** - сколько видимых страниц сейчас грузится

```
картинка в viewport начала грузиться:   visibleUnloadedCount++
картинка в viewport закончила грузиться: visibleUnloadedCount--

visibleUnloadedCount === 0 => hideLoader()
```

* loader живет пока хоть одна видимая картинка не загружена
* фоновые загрузки на счётчик не влияют вообще

---

### DEBOUNCE:

**LOADER_DELAY_MS = 300**

```
scheduleLoader():
  если уже показан или таймер уже тикает => пропустить
  иначе: setTimeout(300ms) => если visibleUnloadedCount > 0 => показать
```

* смысл: быстрые загрузки (< 300мс) проходят незаметно
* юзер вообще не видит спиннер при нормальном скролле
* спиннер появляется только если картинки реально не успевают

---

### ИСКЛЮЧЕНИЯ:

**чистое открытие (open)** - показываем сразу без задержки:

```
showLoaderNow() => загрузчик мгновенно
```

* потому что юзер явно ждет первый рендер, нечего тянуть

**навигация (handleNavigation)** - тоже сразу:

```
showLoaderNow() => ... загрузка ... => hideLoader()
```

* пользователь нажал кнопку "перейти к странице X" - он знает что ждёт

---

### СХЕМА:

```
пользователь скроллит
        |
        v
картинка в preload zone (2500px)?
        |
       да => тихая фоновая загрузка, счетчик не трогать!
        |
        v
картинка в viewport?
        |
       да => visibleUnloadedCount++, scheduleLoader()
        |
        v
прошло 300ms, счётчик > 0?
        |
       да => показываем спиннер (юзер реально ждёт)
        |
        v
загрузилась => visibleUnloadedCount--
счётчик === 0 => hideLoader()
```
